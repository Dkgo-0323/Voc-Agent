# 数据处理、质量评分与情感判断规则

本文对应 2026-11-08 当前代码。当前系统按“方面提及”分析：同一评论可以同时有“续航正向”和“噪声负向”，不是给整篇评论只贴一个情感标签。

## 本次落实的修改

- 之前已将摘录上限从 60 改为 120 字符，并加入按具体方面判断情感的提示词。
- 本次将人工确认的 3 条误判从 positive 改为 neutral，sentiment_score 从 1 改为 0。
- 按现有公式重算三条质量分数，分别仍为 0.891、0.681、0.716。
- PostgreSQL 与 Milvus 的情感和质量元数据已核验一致。复用原有向量，没有新增模型调用。
- 价格评价有歧义的那条保留待审，未强制改标签。
- 修改回执：`artifacts/runtime/sentiment-correction/result.json`；逐条审查：`artifacts/runtime/length-120-retest/sentiment-audit.json`。

提示词约束已经修改，但新提示词能否稳定改善模型情感判断，还需要另行做真实效果复测；本次三条数据纠正来自人工核查。

## 处理流程

原始评论入库 → 预筛选 → 模型抽取方面、情感、证据 → 代码校验 → 固定公式评分 → 保存方面提及 → 向量化 → 看板/检索按质量阈值读取。

| 阶段 | 当前实现 | 代码入口 |
| --- | --- | --- |
| Amazon 文件导入 | 正文少于 20 字符跳过；按 platform + external_id 去重；保存评分、时间、SKU 等信息 | `pipelines/ingestion/amazon_loader.py` |
| 抽取前预筛选 | 正文少于 30 字符跳过；过滤仅物流相关内容；当前只处理英文 | `prepare_document()` |
| 长文本处理 | 超过 3000 字符时截取到约 2000 字符，并尽量在句子边界结束 | `prepare_document()` |
| 模型抽取 | 固定 18 个方面标签；每篇最多保留前三个候选；抽取情感、模型置信度、原文证据 | `prompts.py`、`AspectExtractor` |
| 证据校验 | 解析 JSON 和文档 ID；摘录长度 1–120；必须是原文连续片段；检查标签证据 | `_validate_payload()` |
| 评分与保存 | 计算 0–1 质量分数，与文档处理状态一起保存 | `quality_scorer.py`、`backend/worker/jobs.py` |
| 向量化 | 保存 1024 维向量及 SKU、方面、情感、周、质量元数据 | `embedder.py`、`milvus_repo.py` |
| 展示与检索 | 默认采用质量分数 >= 0.55 的提及，并过滤未启用的 SKU | `settings.py`、`aspect_repo.py` |

导入的 20 字符门槛和抽取的 30 字符门槛是两个阶段，互不等价。原始评论已入库，也可能在抽取前被过滤。

物流过滤实际是简单子串匹配：正文包含 shipping/arrived/package/delivery/fedex/ups，且不包含 battery/power/charge/solar 等产品词时跳过。这不是完整的物流语义分类器，也可能误判。

## 什么是“有效证据”

这些是代码执行的约束，不依赖模型自觉遵守：

1. 只能引用本次提供的文档，不能缺失、重复或引入未知文档 ID。
2. 方面属于固定标签集合，情感只能是 positive / negative / neutral，置信度在 0–1 范围内。
3. `mention_text` 最多 120 字符，且 `mention_text in body` 必须为真。大小写修改、拼写修正、拼接句子都会导致不匹配。
4. “great product”“love it”等泛泛赞美通过正则识别后丢弃。
5. 部分方面必须出现对应关键词。例如太阳能方面需要 solar/panel/PV 等；客服方面需要 support/service/refund 等；家庭备用方面包括 home/outage/blackout/emergency power 等，以及修复后带上下文的停电、来电表达（见文末）。
6. 上述关键词通常检查摘录周围最多 200 字符的原文窗口。同一证据复用多个场景标签时会去重。

标签关键词是必要条件式的粗筛，不能证明语义分类一定正确。目前也不是所有方面都有专门的关键词约束。

有效提及可保留，无效提及丢弃；某篇所有候选均无效时，文档标为 failed。模型返回空方面列表则可以正常结束，因此 embedded 不代表一定产生了证据。向量化失败时保留 enriched，供后续恢复。

## 如何计算质量分数

准确说，当前计算的是“方面提及的分析可用性”，不是判断评论真假，也不是评论满意度。

```python
quality = (
    0.35 * specificity
    + 0.30 * adjusted_confidence
    + 0.20 * length
    + 0.15 * source
)
```

权重在 `pipelines/enrichment/quality_scorer.py` 中以常量写死。

| 分项 | 具体硬编码规则 |
| --- | --- |
| 具体程度 specificity | 有数字 +0.3；有 better/than/faster 等比较词 +0.2；不是泛词 +0.2；属于续航/充电/太阳能/AC 输出/接口这五个核心方面 +0.2；摘录为 20–60 字符 +0.1；最高 1 |
| 置信度 adjusted_confidence | 使用模型给出的 confidence；Amazon 评分 >=4 星却抽取为负向时，将置信度乘 0.7 |
| 长度 length | 摘录长度 + 上下文长度少于 50 得 0.3；50–300 得 1；超过 300 得 0.6 |
| 来源 source | Amazon 有评分得 0.9，无评分得 0.7；Reddit 来源分 >10 得 0.8，否则 0.6；其他来源 0.5 |

补充细节：

- 泛泛赞美在评分器里还会被封顶到 0.35，通常在更早的证据校验阶段就已被丢弃。
- 摘录已允许 120 字符，但具体程度的短摘录奖励仍限于 20–60 字符。61–120 字符合法，只是没有额外的 0.1 分项奖励；本次没有改评分公式。
- 长度分会把摘录与包含该摘录的上下文长度相加，它是启发式指标，不是去重后的有效信息长度。
- Reddit 的高来源分分支需要调用者传 `source_score`；当前常规 `build_aspect_mentions()` 没传这个参数，因此该路径按 0.6 计。
- 0.55 是配置默认阈值，可由环境配置改变。一般是在读取/检索时过滤，而不是所有低分提及都拒绝落库。
- 数字、来源和模型置信度这些信号不证明真实性。0.891 也不表示“89.1% 概率正确”。

高星负向折扣也是当前启发式选择，并非可靠性定律：一篇五星评论完全可能对噪声不满意。它可能低估有价值的局部负向，应作为后续单独评估的规则，不能据此把负向改成正向。

## 如何判断情感倾向

情感不是由质量分数决定。当前流程是：模型阅读原文，按提示词选择标签；代码只做枚举、证据和结构等校验。

| 标签 | 应有的依据 | 例子 |
| --- | --- | --- |
| positive | 对该方面的明确赞许，或清楚描述实际收益 | “客服很快给我换新，解决了问题” |
| negative | 对该方面的明确不满，或清楚描述问题 | “充电太慢”“风扇太吵” |
| neutral | 事实陈述或使用意图，没有足够评价 | “充满需 7–8 小时”“打算带去露营” |

判断必须结合上下文：

- “买来露营，旅行时给手机供电一整天，很满意”可以支持正向。
- “打算露营，但还没出发；在家取暖很满意”不能把家中取暖的满意转给露营。
- “7–8 小时充满”不能单独算充电快，也不能因为另一个句子抱怨阴天就自动改成充电慢。
- “有两个 USB-C 接口”是事实；如果同方面上下文明说接口数量很满意，可以评价配置正向，但不能推断接口性能已实测。

这些语义要求写在 `prompts.py` 的 `ASPECT-LEVEL SENTIMENT RULES` 字符串中。它们是给模型的指导，并不是 Python 条件句硬性保证。例如，目前没有一段代码能全面确认“这句话确实是正向”。

代码固定把 positive 映射为 +1、neutral 为 0、negative 为 -1，供统计使用。它只转换标签数值，不执行情感理解。

## 哪些算硬编码，哪些不算

| 类型 | 当前例子 | 执行保障 |
| --- | --- | --- |
| 常量、正则、条件判断 | 长度上限、关键词白名单、原文匹配、分数权重 | 条件不满足就拒绝或按固定公式计算 |
| 配置默认值 | 0.55 门槛、模型名称、1024 维 | 可由配置修改；不等于业务理解能力 |
| 固定提示词 | 事实中性、方面内情感、不要继承整体情绪 | 模型可能违反，需要标注样本与真实复测验证 |
| 人工校正 | 本次三个 positive → neutral | 只修正已审查记录，不能自动推广到全部评论 |

因此，“代码保证证据可追溯”和“模型正确理解情感”是两个需要分别验证的目标。

## 数据质量验收后的修复

- 家庭备用的原有 outage / blackout 词形已支持复数。
- 新增 power failure、power went out、knocked the power out、when no power available、power came back on 等表达的校验分支。
- 新分支要求原文窗口同时包含家用负载（如灯、冰箱、呼吸机、手机）或电网/天气背景，并排除已列出的设备自身断电、恢复供电表达。
- 这些仍是有限关键词启发式，不能完整判断所有停电语义。原有 home 等词匹配分支仍存在，不应将本次反例测试通过解释为所有家庭备用误判均已解决。
- 72 项离线回归测试通过。六条人工建议漏提取证据经真实校验器的通过数从 4 增至 6；这不是模型实际召回测试，也没有把六条建议直接落库。
- 本轮另外修复两条情感误判；错误方面与弱引用修正的双库回执位于 `artifacts/runtime/quality-evidence-correction-v2/`。原始验收快照保留在 `artifacts/runtime/quality-acceptance/`。

## 可选的编号证据实验模式

新增 `ENRICHMENT_EVIDENCE_MODE=spans`：代码先给原文短句/子句编号，模型只选择编号和标签，代码按原始偏移取回证据。未知编号、跨文档不合法编号、冲突的自写摘录会被拒绝；这是代码约束，不依赖模型精确复制空格。

默认仍为 `ENRICHMENT_EVIDENCE_MODE=text`、`ENRICHMENT_BATCH_SIZE=10`。可把批量设为 1 进行逐篇实验，但请求次数会增加，需要重算模型调用预算。对照测试未全部通过，因此未修改用户业务 `.env` 启用实验模式，也未重写已有业务数据。

固定六条问题样本的目标方面命中从 2/6 改善到 5/6，方面与情感同时命中从 2/6 改善到 4/6；不能外推为全库准确率。详细测试与未解决问题见 `artifacts/runtime/multiaspect-span-recall/REPORT.md`。
